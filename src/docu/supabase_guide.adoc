== Überblick
Kurzer Überblick, wie Supabase aktuell genutzt wird: Auth läuft weiterhin über Supabase, aber ausschließlich serverseitig. Das Frontend spricht nur die Express-API, die DB-Zugriffe übernimmt Prisma.

== Clients & Umgebungsvariablen
* Backend: `SUPABASE_URL` und `SUPABASE_ANON_KEY` werden in link:../../src/backend/src/supabaseAuth.js[backend/src/supabaseAuth.js] genutzt, um gegen die Supabase Auth-REST-API zu authentifizieren. `DATABASE_URL` (Supabase-Postgres) bleibt für Prisma.
* Frontend: Kein Supabase-Client mehr. API-Basis per `REACT_APP_API_BASE_URL` (Fallback `http://localhost:5000`); im Repo ist link:../../src/frontend/.env[frontend/.env] auf `http://localhost:3001` gesetzt.
* Docker-Dev: `docker-compose.dev.yml` lädt `backend/.env.local` und `frontend/.env`.
* Docker-Prod: `docker-compose.prod.yml` lädt `backend/.env.production` (falls vorhanden) und `frontend/.env`.

== Auth-Flow (Backend-first)
* Auth-Endpunkte: link:../../src/backend/src/routes/auth.js[backend/src/routes/auth.js] kapselt `login`, `register`, `session` (Token-Validierung) und `logout` per Supabase-REST.
* Middleware: link:../../src/backend/src/middleware/authenticate.js[backend/src/middleware/authenticate.js] validiert `Authorization: Bearer <token>` gegen Supabase und hängt `req.auth.user` an.
* Frontend-Integration: link:../../src/frontend/src/api/authApi.js[frontend/src/api/authApi.js] ruft nur Backend-Endpoints auf, persistiert Token/User in `localStorage`. `App.jsx` lädt eine gespeicherte Session und reicht `session` an `HabitsPage` weiter.

== Datenmodell (Supabase Tabellen)
* Tabelle: `habits_table` (siehe Prisma-Schema link:../../src/backend/prisma/schema.prisma[schema.prisma]) mit Feldern `id` (String mit `uuid()`-Default), `userId` (String), `habit_name`, `description`, `start_date`, `streak`, `last_break`, `last_checked`, `prev_last_checked` (array/timestamptz).
* Tabelle: `users` mit `id` (String mit `uuid()`-Default) sowie `animal_type` und `animal_mood`.
* Erwartung: `userId` in `habits_table` entspricht Supabase-Auth-User-ID (`req.auth.user.id`).

== Datenzugriff über das Backend
* Habit-Routen: link:../../src/backend/src/routes/habits.js[backend/src/routes/habits.js] implementiert `GET /api/habits`, `POST /api/habits`, `PUT /api/habits/:id`, `DELETE /api/habits/:id`, `POST /api/habits/:id/toggle` auf Basis von Prisma. Business-Logik (Toggle, Streak, Reset nach 48h) liegt im Backend.
* User-Routen: link:../../src/backend/src/routes/users.js[backend/src/routes/users.js] implementiert `GET /api/users/animal` und `PUT /api/users/animal` für `animal_type`/`animal_mood`.
* API-Client im Frontend: link:../../src/frontend/src/api/httpClient.js[frontend/src/api/httpClient.js] baut Requests mit optionalem Bearer-Token; link:../../src/frontend/src/api/habitsApi.js[frontend/src/api/habitsApi.js] und link:../../src/frontend/src/api/userApi.js[frontend/src/api/userApi.js] konsumieren die Routen.
* UI-Verbrauch: link:../../src/frontend/src/pages/HabitsPage.jsx[frontend/src/pages/HabitsPage.jsx] ruft die API-Funktionen auf und reicht Daten an Grid/Kalender weiter.

== Sicherheit / RLS
* Supabase Row Level Security weiterhin sinnvoll: Policies sollten `userId = auth.uid()` (bzw. den tatsächlichen Spaltennamen) erzwingen.
* Token-Verifikation passiert serverseitig; der Browser sieht keine DB-Credentials oder Supabase-Keys mehr.

== Typische Fehlerquellen & Checks
* 401/403: Prüfe gültiges `Authorization`-Header zum Backend; Backend meldet Supabase-Fehler in `detail`.
* Leere Daten nach Login: `userId` der Zeilen muss mit Supabase-Auth-User übereinstimmen.
* BigInt im Backend: Serialisierung erledigt `serializeHabit` in link:../../src/backend/src/routes/habits.js[backend/src/routes/habits.js]; `streak` wird als Number zurückgegeben.
* Toggle-Logik läuft im Backend; falls alte Daten `prev_last_checked` nicht als Array vorliegen, prüfe DB-Einträge auf gültige Arrays.
